# 性能

两部分：播放时每帧的开销（含配置要求和自动画质），以及从拿到音频到能播放的准备时间。

测量机器：i9-14900HX，RTX 5070 Ti 笔记本（独显直连），32 GB 内存，2560×1600 300 Hz、缩放 150%。网易云 3.1.37（Chrome 91）+ BetterNCM 1.3.4；无头 Edge（ANGLE D3D11）。机器上有其他渲染任务时绝对值会翻 2–3 倍，比较只看同一时段交替跑的 A/B。

## 配置要求

README 只写结论，依据在这里。显卡数字是**估算**：只在上面一台机器上测过，集成显卡没有实测，按公开跑分的比例换算。

| | 1080p 窗口 | 说明 |
|---|---|---|
| 独显推荐 | GTX 1650 / RTX 3050 及以上，画质“自动”（默认）或“高” | 每帧中位约 5–7 ms，转场约 12–18 ms，60 帧有余量 |
| 独显 2K / 4K | RTX 3060 / 4060 及以上 | 像素是 1080p 的 1.8 / 4 倍，开销大致按像素增长 |
| 集显推荐 | Iris Xe（96 EU）、Radeon 680M / 780M 及以上，画质“中”或“低” | 原生 1080p 下抒情风格和重场景掉到 40–50 帧；“中”在 125% 缩放的笔记本上只画 64% 的像素 |
| 集显最低 | UHD 620 一级，画质“低”、帧率上限 30 | 原生 1080p 下每帧约 50 ms；“低”约 20–40 帧 |
| 显存 | 1080p 约 0.5 GB 渲染缓冲，4K 约 2 GB | 另有场景纹理和网易云自身占用（网易云 GPU 进程实测 1.3–2.1 GB） |
| 必须 | 网易云“设置 → 常规 → 开启GPU加速” | 关闭时网易云带 `--disable-gpu` 启动，WebGL 落到 SwiftShader 软件渲染 |

“自动”最低只降到原生像素的一半（见“自动画质”），集成显卡多半仍要手动选“中”或“低”。

换算依据：各风格在 1813×1176（约等于 1080p 的像素量）上每帧 GPU 中位 0.7–2.3 ms（抒情最重），转场等 p95 约 3–6 ms，最重的场景夜城 3.7 ms、光斑 3.1 ms（无头 Edge；网易云里同一场景约低两成）。按 3DMark Time Spy 显卡分取倍数：RTX 4060 笔记本约慢 1.4 倍，RTX 3050 笔记本约 3 倍，GTX 1650 约 4 倍，Radeon 780M 约 5 倍、680M 约 6 倍，Iris Xe 约 8–11 倍，UHD 620 约 30 倍。集显受内存带宽限制更重，实际可能更差。

**CPU**：网易云里不限帧率能到 250–290 帧（屏幕 300 Hz），`player.frame` 每帧 0.5–0.7 ms。按单核性能粗算，近几年的四核笔记本 CPU 画 60 帧应有余量，未在弱 CPU 上实测。

## 测量工具（`tools/bench/`，不打包）

- `run.ts` + `inpage.ts`：网易云带 `--remote-debugging-port=9222` 启动，经 CDP 把 `inpage.ts` 注入页面，包住 `window.__betterMv.player`（真实窗口、真实帧循环）。每帧记 CPU 时间（`player.frame`）和 GPU 时间（`EXT_disjoint_timer_query_webgl2`，只支持 TIME_ELAPSED 且不能嵌套：要么一帧一个查询，要么每次 `renderer.render` 一个并按后期通道归类）。可强制场景、风格、画风、镜头与成片后期开关、像素比、帧率上限，并定位到同一段。旁边用 `typeperf` 采网易云各进程的 CPU、GPU 3D 引擎占用和专用显存。`mode: 'cpu'` 只记 CPU、不发 GPU 查询。
- `headless.ts`：开发页放进无头 Edge，逐帧驱动、只量 GPU。与宿主无关的部分（着色器、通道、分辨率缩放、画面对比、泄漏）在这里测；`--root` 指向另一份代码（如 `git archive HEAD` 导出）做 A/B；`switch` 复现换歌时的长任务；`stills` 截对比帧。帧节奏和主线程只能在网易云里测。
- `diff.py` 逐像素对比两组截帧，`table.ts` 把结果排成表。
- 注意：网易云窗口最小化时页面 `hidden`、没有动画帧，脚本会先把窗口调到前台。窗口被完全挡住但未最小化时照常绘制（网易云禁用了 Chrome 的遮挡计算 `CalculateNativeWinOcclusion`）。`plugins_dev` 变化时 BetterNCM 会重载页面，重载后整页变慢，装构建前先退出网易云。

## 播放时的帧耗时

### 热点

无头 Edge，37 个场景逐个强制，每帧 GPU 中位，1813×1176（ms）：

| 场景 | 优化前 | 优化后 | 主要花在 |
|---|---|---|---|
| 夜城 | 4.8 | 3.7 | 场景本身 3.0（地面着色器），景深 0.9 → 0.5 |
| 光斑 | 4.0 | 3.1 | 场景本身 2.7 |
| 三角 / 悬城 / 门格回廊 | 3.1 / 2.7 / 2.5 | 2.3 / 1.9 / 1.8 | 分形光线步进 1.7–2.3 |
| 云海 | 3.3 | 2.3 | 光线步进 2.1 |
| 雨窗 | 3.3 | 2.1 | 场景本身 1.9 |
| 极光、光柱、浮雕、唱片、细分 | 2.0–2.6 | 1.3–2.0 | 景深 / 运动模糊 0.3–0.8 |
| 其余 26 个 | 1.1–2.0 | 0.6–1.3 | 后期占一半以上 |
| 37 个场景的中位 | 1.65 | 0.71 | |

按风格整段（自动编排，drop 段 4 s × 3）：律动 2.1 → 1.0，抒情 3.4 → 2.1，字 1.6 → 0.7，墨 1.7 → 0.8 ms；画风另加 0.2–0.6 ms。p95 约是中位的 2–3 倍，主要来自转场（两个场景同时画）。

分辨率：律动在这块卡上低于约 0.95 MP 后不再变快（约 0.6 ms 固定开销），抒情基本按像素线性（1813×1176 1.67 ms → 846×548 0.43 ms），弱显卡上更接近线性。关泛光省约 0.17 ms，关镜头和成片后期合计省约 0.17 ms。

网易云里（1813×1176，不限帧率）：帧率 190–290，每帧 CPU 中位 0.5–0.7 ms，GPU 中位 0.6–1.3 ms、p95 1.7–2.8 ms。

### 已做的优化

1. **后期缓冲不用 4× MSAA**（`engine.ts`、`shots.ts`）：composer 的两个缓冲原来是半精度 + 4× MSAA + 深度，每个全屏通道（泛光合成、grade、成片）都写进多重采样缓冲再解析，1080p 下还多占约 220 MB。改成单采样、无深度；场景本身仍画进 ShotPass 自己的 MSAA 缓冲，“无镜头、无转场”时先画进 rtB 再拷贝。每帧 1.65 → 0.89 ms；渲染缓冲显存 1080p 约 680 → 490 MB，4K 约 2.7 → 2.0 GB。
2. **渲染目标采样用 `textureLod(…, 0.0)`**（grade、镜头、转场的 tA / tB、画风）：D3D 编译器（FXC）会把分支和循环里带梯度的采样压平执行，grade 的缩放模糊（10 次）和拖影（12 次）循环每个像素都在跑。渲染目标没有 mipmap，结果逐像素相同；封面和字形图集有 mipmap，不改。0.89 → 0.71 ms。
3. **粉尘取点不读回 GPU 画布**（`text.ts` 的 `inkPoints`）：原来每个词第一次碎掉时对整张文字画布 `getImageData`，加速的 2D 画布要从 GPU 读回，一行字可达几十到上百毫秒。现在在约 9000 像素的小画布上按同样笔画重画再取点，约 2 ms，点位差 1–2 个纹理像素。
4. **预热覆盖播放中才编译的材质**（`textPrimer` / `primer`）：粉尘粒子、带贴图的文字、“书写”效果的文字、光斑里可虚焦的文字原来要等第一次出现才编译（卡 100–150 ms）。现在叠加层和各歌词组里各放一个隐藏样本，预热会编译隐藏物体，样本也一直持有程序。样本的包围盒设为空，否则会改变镜头对焦（对焦用歌词组的包围盒）。
5. **换歌时释放场景私有资源**（`MvScene.dispose`，`MvPlayer.unload` 调用）：歌词印层、画布的绘画缓冲和内部场景、云海和分形的步进缓冲、光柱的状态缓冲都不在场景树里，原来每首歌留下一份（反复重新编排 24 次，几何体 596 → 1076、纹理 330 → 486）。现在只释放几何体、材质和自有缓冲，不释放纹理（云海的噪声体按渲染器缓存、跨歌复用）。

验证：每项都与 HEAD 在同一首歌、同一 seed、同一时刻逐像素比对（4 种风格 × 42 个时刻，37 个场景 × 3 个时刻），差异只在叠加层线条端点（原来靠 MSAA 抹平的几个像素）和正在碎成粉尘的词（随机挑的粒子不同）。

稳定性（无头 Edge）：同一编排连续 10 分钟，JS 堆 174–208 MB 来回，纹理填满缓存后不再增长，几何体不持续上涨；24 次重新编排后资源数不再增长，重画的帧与第一次逐像素相同；七种窗口尺寸来回切换无报错、资源数不变。网易云里列表循环 10 分钟（5 首），GPU 进程显存 1.3–2.1 GB 随歌升降，换歌后纹理、几何体回落。

### 自动画质

画质“自动”档（默认）：按 MV 每帧在显卡上的实际耗时，在三档像素比之间切换。代码在 `src/app/governor.ts`，帧循环接入是 `src/plugin/main.ts` 的 `govern()`。

- **档位**：第一档就是“高”（屏幕原生，最高 2 倍），每降一档约少 30% 像素，最低一半像素，景深和动态模糊始终保留。150% 缩放的屏幕上是 1.5 → 1.26 → 1.06 倍，100% 上是 1 → 0.84 → 0.71 倍。最低档定在这里，是因为 0.89 倍起文字和细线明显变软。更弱的显卡要手动选“中”或“低”。
- **量什么**：插件自己每帧的 GPU 时间（一帧一个 TIME_ELAPSED 查询，结果晚几帧取回），转场帧不计。没有该扩展时改看帧间隔，只降不升。其他程序占用显卡不计入：它们的绘制排在插件两帧之间，插件这一帧的 GPU 时间不变（另开页面占去约七成 GPU 时实测如此）。所以“自动”只在 MV 本身画不动时才降。
- **何时降**：只在切镜时换档，连续运镜的一组镜头中间不换。最近约 2 s 里较慢的四分之一帧超过帧预算（60 帧 16.7 ms，帧率上限 30 时 33.3 ms）的 85% 就降一档，换档后 3 s 内不再动。
- **何时升**：在当前档停满 15 s，并且换档以来每个镜头的较慢帧（p90）按像素换算到上一档后仍留出三分之一预算。升上去不到一分钟又降回，下次升档的等待加倍，最长 4 分钟。只看最后一个镜头不行：场景耗时差好几倍，模拟 GTX 1650 一级时抒情和字会在轻场景升档、到重场景又降回，40 s 里来回 4 次。
- **测量时关闭**：TIME_ELAPSED 不能嵌套，`tools/bench/inpage.ts` 注入时把 `window.__betterMv.governed` 设为 false，由测量自己定分辨率。
- **不降档时画面不变**：第一档就是“高”的像素比，计时查询不影响绘制。

验证（无头 Edge，真实 GPU 计时，把预算除以 k 模拟慢 k 倍的显卡：4 倍约 GTX 1650，6 倍约 680M，10 倍约 Iris Xe）：

| 模拟 | 结果 |
|---|---|
| 本机，4 种风格各 2 分钟 | 不换档，较慢帧 p90 约 3–4 ms（降档线 14.2 ms） |
| 慢 2.5 倍 | 不换档 |
| 慢 4 倍 | 律动、字、墨各降一档，抒情降到最低；都没有再升 |
| 慢 6 倍 | 律动、抒情、字降到最低，墨降一档；都没有再升 |
| 慢 10 倍 | 4 种风格都在 5–17 s 内降到最低 |
| 慢 10 倍 20 s / 正常 75 s 交替 | 加负载后 7–15 s 降到底；去掉后 24–28 s 回到第一档；第二轮等待加倍，49–53 s 回到第一档 |

网易云里：本机正常播放 3 分钟、21 个场景不换档；把档位放大到 4 / 3.36 / 2.82 倍模拟慢卡时，150 s 里换档 3 次，间隔都在 20 s 以上且都在切镜处；从最低档恢复到第一档约 38 s；窗口最小化时不画也不计时，还原后清空旧采样、档位不变。

## 准备时间

从拿到音频到能播放：解码 → 分析 → 建场景（`player.load`）→ 预热（`player.warm`）。

《Falling Again》（33 MB FLAC，4 分 29 秒），无头 Edge：

| 阶段 | 优化前 | 优化后 |
|---|---|---|
| 解码 | 两次（22.05 kHz 单声道 + 44.1 kHz 立体声）约 0.8 s | 一次，约 0.4 s |
| 分析（V8） | 约 0.6 s，分片之间等帧 | 约 0.45 s，不等帧 |
| 建场景 | 约 0.5 s | 第一首约 0.5 s，之后约 0.05 s |
| 预热 | 4.9–5.4 s | 第一首 1.1–1.6 s，之后同场景几乎为 0 |
| 第一帧 | 卡片 107 ms、极光首次出现 147 ms | 约 20 ms，无尖峰 |

合计约 7 s → 约 3 s。

### 着色器编译

网易云的 Chromium 在 Windows 上把 WebGL 翻成 HLSL，由 FXC 编译，很慢，而且**每个函数调用都内联、常数次数的循环都展开**。夜城地面着色器里 `lightRow` 写了三十多处调用，一个程序编译 2.2–2.4 s。

- **并行编译**：`Engine.compile` 用 three 的 `compileAsync`（`KHR_parallel_shader_compile`），所有场景的程序在 GPU 进程里一起编，页面不卡。没有这个扩展时退回同步编译。
- **场景自己的离屏通道**（`onBeforeRender` 里另画的场景或全屏四边形）不在场景树里，`compileAsync` 找不到，要在 `MvScene.offscreen` 里登记（全屏四边形用 `passMesh(material)`）。云海、画布、光柱、分形都这样做。
- **后期链**（泛光、调色、转场、画风）用 `Engine.compilePost`，屏幕和离屏两种目标都编（程序随目标不同）。
- **颜色用 uniform，不写进源码**：源码随封面变就每首都得重编；源码不变，第二首起直接复用程序。数值按原来写进源码时的位数取整，画面逐像素不变。跨重启的磁盘着色器缓存不可依赖。
- **提前编译**：与歌无关的程序（夜城、极光、后期链）在 `MvPlayer` 构造时就开始编，与读歌、分析重叠。
- 把夜城的重复调用收进循环、参数查表能把编译从 2.2 s 降到 0.7 s，但运行时每帧多 0.3–0.4 ms（+11%），没有采用。新写的着色器仍应避免把同一个重函数写几十处调用：能写成循环里调一次的就别展开写。

### 解码

- 只按 22.05 kHz 解码一次，分析用的单声道和示波器用的立体声都从这里来；左右声道差异大到可能是示波器音乐时（很少见）才按 44.1 kHz 再解一次。
- 循环里读 `AudioBuffer.numberOfChannels` 每次都是一次 DOM 调用，会让下混慢十倍；`Math.round` 调一千多万次约 0.1 s，`toStereo` 改用截断写法。
- 按 44.1 kHz 解码再用 JS 半带滤波降采样，JS 部分要 80–275 ms，抵掉了浏览器重采样省下的 0.1–0.2 s，没用。

### 分析

- FFT（`fft.ts`）：前两级（旋转因子 1、−i）并进位反转，其余两级一趟，旋转因子表分级连续存放；V8 里 1024 点 9.1 → 4.9 µs。`quantile` 用快速选择代替排序。结果逐项不变。
- 分片之间用 `yieldToPage`（MessageChannel）让出，不等 requestAnimationFrame。
- 剩下的热点：STFT（约一半）、tempogram 的自相关、onset。

### 换歌时的长任务

网易云里连切歌时，每次换歌有 0.5–1.1 s 不出帧（等待页动画停顿）。无头 Edge 用 `headless.ts switch` 复现（3 首歌，各 20–24 个场景，每次 0.42–0.53 s），由三段组成：

1. 一个 0.25–0.36 s 的 JS 任务：`prepareSong` 收尾、`player.load` 的场景构造（细分、画布、调试视图、浮雕、字形图集）、`warm` 的同步部分（24 个场景逐个摆到第一个镜头：画歌词、粉尘取点、频谱）。
2. 紧接着 0.15–0.29 s：上一段画的 2D 画布在任务结束时一起提交（`RasterCHROMIUM`）；帧循环在 load 之后就开始画新歌（等待页盖着看不见），第一帧碰到正在并行编译的程序，`getProgramInfoLog` 同步等待。
3. 预热逐场景绘制，每个 50–180 ms：`getProgramInfoLog` / `getProgramParameter` 同步等 GPU 进程做完上一个场景的活。

改法：

- **建场景分片**（`MvPlayer.loadInSlices`）：load 写成生成器，同步的 `load()` 一次走完（开发页、OBS 页、宣传片、bench 照旧）；插件准备新歌时在规划镜头后、每个场景构造后、字形图集后各让出一次。准备被取消时卸掉建了一半的；另一次 load 开始时停下。
- **单个场景内部分步**：画布的整首笔画规划每 1024 步让出，细分球每级让出两次，字形图集每 64 个字让出（`CanvasScene.building`、`SubdivideScene.building`、`GlyphAtlas.building`），一次建完时用 `finish` 走完，结果逐位相同。
- **预热分片**：每个场景摆好后立刻开始编译它的程序，场景之间让出；全部编完后逐个绘制，下一个等 GPU 做完上一个（`Engine.idle`：WebGL2 fence，在让出之间查询，最多等 1 s，连续超时 3 次后不再使用）。绘制前先对已编好的程序读一次信息（`getUniforms`，此时 GPU 空闲），绘制本身不再同步等待。
- **准备中的歌不画**：帧循环在这首歌预热完之前不画它。
- **`prepareSong` 收尾**：封面取色、立体声峰值、转换之间各让出一次。
- **OBS 歌曲文件**：序列化不再触发封面纹理的 PNG 编码，200 ms → 24–29 ms，放在单独任务里（见 [OBS.md](OBS.md)）。
- **等待页提前撤掉**：建场景期间又触发一次准备（例如打开 MV 页）时，正在建或预热的歌不算“已在显示”。建场景被别的加载打断时改为一次建完；关掉再打开 MV 时，被取消的准备不再挡住新的准备。

结果：

| | 改前 | 改后 |
|---|---|---|
| 无头 Edge：最长不出帧 | 0.42–0.53 s | 无超过 50 ms 的 |
| 无头 Edge：读完音频到预热完 | 1.41–1.73 s | 1.34–1.64 s |
| 网易云：准备期间最长不出帧 | 0.54–1.11 s | 63–143 ms |
| 网易云：准备期间超过 50 ms 的帧间隔 | 每次 8–40 个 | 每次 0–7 个 |
| 网易云：切歌到 MV 第一帧 | 2.5–8.8 s | 3.4–7.7 s |

网易云的 Chromium 91 跑这些 JS 比无头 Edge 慢 3–4 倍。切歌那一下还有 83–133 ms 是网易云自己处理切歌（redux 分发与订阅），插件只占其中 10–20 ms。画面与改前逐像素对比只差噪声，`bun run eval` 逐项相同。

### 提前分析下一首（设置 `prefetch`，默认关）

- `main.ts` 的 `prefetchNext`：当前歌准备完、开关打开、播放列表或位置变化时，用 `client.ts` 的 `nextSong` 找下一首（顺序、列表循环；单曲循环、随机、FM、心动模式无法预知，不做），后台 `gather`（读音频、歌词、百科、封面 → `prepareSong`），完成后放进 `ready`。
- 节奏：`whenIdle`（requestIdleCallback，最迟 0.5 s）+ 3 ms 分片，只用帧间剩余时间。边播边预读时帧间隔不变差（最长 23 ms），约 0.9 s 准备完；单声道下混、`toStereo` 各约 20 ms 的同步计算可能丢一两帧。
- 预读未完成就切到这首：`prepareCurrent` 接手同一个任务，改成全速并显示进度；切到别的歌、关掉 MV 或关掉开关就取消。
- 首次歌词对齐推迟到歌真正显示时（`alignIfNeeded`）：预读的歌把音频留到那时（`toAlign`），用过即释放。

### 缓存

- 夜城楼群布局与歌无关，生成一次（约 0.25 s）后保留。
- 云海的两块 3D 噪声按渲染器烘焙一次后保留。
