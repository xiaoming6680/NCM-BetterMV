# 性能：准备时间与着色器

从拿到音频到 MV 能播，依次是：解码 → 分析 → 建场景（`player.load`）→ 预热（`player.warm`）。2026-10-13 做过一轮优化，本文记录做法、实测和写场景时要守的规则。

## 实测（2026-10-13）

《Falling Again》（33 MB FLAC，4 分 29 秒），dev 未打包，无头 Edge（ANGLE D3D11，RTX 5070 Ti 笔记本）：

| 阶段 | 改前 | 改后 |
|---|---|---|
| 解码 | 两次（22.05 kHz 单声道 + 44.1 kHz 立体声）约 0.8 s | 一次，约 0.4 s |
| 分析（V8） | 约 0.6 s CPU，分片之间等帧 | 约 0.45 s，分片之间不等帧 |
| 建场景 | 约 0.5 s | 第一首约 0.5 s，之后约 0.05 s（夜城楼群只生成一次） |
| 预热 | 4.9–5.4 s | 第一首 1.1–1.6 s，之后同场景几乎为 0 |
| 第一帧 | 卡片 107 ms、极光首次出现 147 ms | 约 20 ms，无尖峰 |

合计（音频到手后）约 7 s → 约 3 s。机器上有别的渲染任务时数字会翻 2–3 倍，比较只看同一时段的 A/B。测量脚本在会话的 scratchpad 里（`flow.ts` 全流程、`probe.ts` 单场景编译、`frames.ts` + `cmp.ts` 逐像素对比、`gpu.ts` 帧耗时），没有入库。

## 着色器编译（最大头）

网易云的 Chromium 在 Windows 上把 WebGL 翻成 HLSL，由 D3D 编译器（FXC）编译，很慢，而且**每个函数调用都内联、常数次数的循环都展开**。夜城地面的着色器里 `lightRow` 写了三十多处调用，一个程序编译 2.2–2.4 s。

- **并行编译**：`Engine.compile` 用 three 的 `compileAsync`（`KHR_parallel_shader_compile`），所有场景的程序在 GPU 进程里一起编、页面不卡；`warm()` 之后只剩上传缓冲和纹理。没有这个扩展时退回同步编译，不会更差。
- **场景自己的离屏通道**（`onBeforeRender` 里另画的场景或全屏四边形）不在场景树里，`compileAsync` 找不到：在 `MvScene.offscreen` 里列出来（全屏四边形用 `passMesh(material)`）。云海、画布、光柱、分形图版都这样做。
- **后期链**（泛光、调色、转场、画风）用 `Engine.compilePost`，屏幕和离屏两种目标都编（程序随目标不同）。
- **颜色用 uniform，不写进源码**：源码随封面变，每首歌都得重编；源码不变，同一次使用里第二首起直接复用程序。夜城、极光已改（数值按原来写进源码时的位数取整，画面逐像素不变）。跨重启的磁盘缓存在当前 Edge 上没测到命中，不指望它。
- **提前编译**：源码与歌无关之后，夜城、极光和后期链在 `MvPlayer` 构造时就开始编（插件里播放器在读歌、分析之前创建），和准备阶段重叠。
- 试过把夜城的重复调用收进循环、参数查表：编译 2.2 → 0.7 s，但运行时每帧多 0.3–0.4 ms（+11%，展开的 16 次大街循环反而快），撤回了。新写的着色器仍应避免同一个重函数写几十处调用：能写成一个循环里调一次的，就别展开写。

## 解码与准备

- 只按 22.05 kHz 解码一次，分析的单声道、示波器的立体声都从这里来；左右声道差异大到可能是示波器音乐时（`xyMusic` 的第一关 > 0.3，很少见）才按 44.1 kHz 再解一次做完整判断。
- V8 里的坑：循环里读 `AudioBuffer.numberOfChannels`（每次都是一次 DOM 调用）让下混慢了十倍；`Math.round` 一千多万次约 0.1 s，`toStereo` 换成截断写法。
- 试过按 44.1 kHz 解码再用 JS 半带滤波降到 22.05 kHz（浏览器解码时顺带重采样约多 0.1–0.2 s）：分析结果几乎一样，但 JS 降采样本身 80–275 ms，抵掉了收益，没用。

## 分析

- FFT（`fft.ts`）：前两级（旋转因子 1、−i）并进位反转，其余每两级一趟、分级连续存放的旋转因子表；V8 里 1024 点 9.1 → 4.9 µs。`quantile` 用快速选择代替整段排序。改前改后 5 首本地歌的评测输出逐项相同。
- 分片之间用 `yieldToPage`（MessageChannel）让出，不等 requestAnimationFrame：原来每 8 ms 工作后等一帧，一半时间空等；网易云最小化时 rAF 停掉，分析也跟着停。
- 剩下的热点：STFT 本身（约一半）、tempogram 的自相关、onset。

## 提前分析下一首（设置 `prefetch`，默认关）

- `main.ts` 的 `prefetchNext`：当前歌准备完、开关打开、播放列表或位置变化时，用 `client.ts` 的 `nextSong` 找下一首（顺序播放、列表循环；单曲循环、随机、FM、AI 模式无法预知，不做），在后台 `gather`（读音频、歌词、百科、封面 → `prepareSong`），完成后放进 `ready`。
- 节奏：`whenIdle`（requestIdleCallback，最迟 0.5 s）+ 3 ms 分片，只用帧与帧之间剩下的时间。无头 Edge 实测：边播 MV 边预读，帧间隔没有变差（最长 23 ms，单独播放时 37 ms），约 0.9 s 准备完。还剩几段同步计算（单声道下混、`toStereo` 各约 20 ms），预读时可能丢一两帧。
- 预读没完成就切到这首：`prepareCurrent` 接手同一个任务，改成全速（`yieldToPage`）并显示进度；切到别的歌、关掉 MV 或关掉开关就取消。
- 首次歌词对齐改在歌真正显示时（`alignIfNeeded`）：预读的歌把音频留到那时（`toAlign`），看过一次就释放。

## 缓存

- 夜城楼群的布局与歌无关，生成一次（约 0.25 s）后留着。
- 云海的两块 3D 噪声与歌无关，按渲染器烘焙一次后留着（原来每首都烘、且旧的不释放）。
