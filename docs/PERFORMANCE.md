# 性能

两部分：播放时每一帧的开销与配置要求（2026-10-17），从拿到音频到能播的准备时间（2026-10-13，换歌时的长任务 2026-10-17）。测试记录（各风格、长时间播放、切歌、窗口缩放、后台挂起）在 [TESTING.md](TESTING.md)。

## 配置要求

README 只写一句结论，依据在这里。显卡的数字是**估算**：只在一台 RTX 5070 Ti 笔记本上测过，集成显卡没有实测（这台机器是独显直连，集显被关掉了），按公开跑分的比例换算。

| | 1080p 窗口 | 说明 |
|---|---|---|
| 独显推荐 | GTX 1650 / RTX 3050 及以上，画质“自动”（默认）或“高” | 每帧中位约 5–7 ms，转场时约 12–18 ms，60 帧有余量 |
| 独显 2K / 4K | RTX 3060 / 4060 及以上 | 像素是 1080p 的 1.8 / 4 倍，开销大致按像素涨 |
| 集显推荐 | Iris Xe（96 EU）、Radeon 680M / 780M 及以上，画质“中”或“低” | 原生 1080p 下抒情风格和重场景会掉到 40–50 帧；“中”在 125% 缩放的笔记本上只画 64% 的像素 |
| 集显最低 | UHD 620 一级，画质“低”、帧率上限 30 | 原生 1080p 下每帧 50 ms 上下，跑不动；“低”约 20–40 帧 |
| 显存 | 1080p 约 0.5 GB 渲染缓冲，4K 约 2 GB | 另有场景纹理和网易云自己的占用：网易云 GPU 进程实测 1.2–1.6 GB（1813×1176，优化前） |
| 必须 | 网易云「设置 → 常规 → 开启GPU加速」打开 | 关掉时网易云带 `--disable-gpu` 启动，WebGL 落到 CPU 软件渲染 |

“自动”最低只降到原生像素的一半（见下文“自动画质”），集成显卡多半仍要手动选“中”或“低”。

换算依据：优化后各风格在 1813×1176（约等于 1080p 的像素量）上每帧 GPU 中位 0.7–2.3 ms（抒情最重），转场等 p95 约 3–6 ms，最重的场景夜城 3.7 ms、光斑 3.1 ms（无头 Edge 数字；网易云里同一场景约低两成）。按 3DMark Time Spy 显卡分粗略取倍数：RTX 4060 笔记本约慢 1.4 倍，RTX 3050 笔记本约 3 倍，GTX 1650 约 4 倍，Radeon 780M 约 5 倍、680M 约 6 倍，Iris Xe 约 8–11 倍，UHD 620 约 30 倍。集显受内存带宽限制更重，实际可能比这个比例更差。

**CPU**：机器空闲时，网易云里不限帧率能到 250–290 帧（屏幕 300 Hz），`player.frame` 每帧 0.5–0.7 ms（i9-14900HX）。按单核性能粗算，近几年的四核笔记本 CPU 画 60 帧应有余量，但没有在弱 CPU 上实测。

## 播放时的帧耗时（2026-10-17）

### 怎么测

`tools/bench/`（不打包进插件）：

- `run.ts` + `inpage.ts`：网易云带 `--remote-debugging-port=9222` 启动，经 CDP 把 `inpage.ts` 注进页面，包住插件自己的 `window.__betterMv.player`（真实窗口、真实的帧循环）。每帧记 CPU 时间（`player.frame`）和 GPU 时间（`EXT_disjoint_timer_query_webgl2`，网易云的 Chrome 91 有，只支持 TIME_ELAPSED、不能嵌套：要么一帧一个查询，要么每次 `renderer.render` 一个、按后期通道归类）。可以强制场景（每个镜头都用它）、风格、画风、镜头与成片后期开关、像素比、帧率上限，并把歌定位到同一段。旁边用 `typeperf` 采网易云各进程的 CPU、GPU 进程的 3D 引擎占用和专用显存。窗口最小化时页面 `hidden`、没有动画帧，脚本会先把窗口调到前台。
- `headless.ts`：开发页放进无头 Edge（同样是 ANGLE D3D11），逐帧驱动、只量 GPU。与宿主无关的部分（着色器、通道、分辨率缩放、画面对比、泄漏）都在这里测；`--root` 可以指向另一份代码（例如 `git archive HEAD` 导出）做 A/B。帧节奏、主线程这类只能在网易云里测；只有换歌时把主线程卡住的长任务（`switch`）在这里也能复现。
- `diff.py` 逐像素对比两组截帧，`table.ts` 把结果打成表。

同一时段别的会话在跑视频渲染（其它进程占 GPU 3D 20–40%），绝对数会偏高、尖峰会变多；比较只看同一时段交替跑的 A/B。

### 网易云里（优化前，14 个场景）

《Walk Thru Fire》第一个 drop（41 s 起 4 秒），1813×1176（窗口 1209×784，dpr 1.5，画质“高”），不限帧率，屏幕 300 Hz：

| | 范围 |
|---|---|
| 每帧 GPU 中位 | 1.0–2.3 ms（浮雕、光斑最重） |
| 每帧 CPU（`player.frame`，含读 GPU 查询） | 1.4–4.1 ms（推进最重） |
| 帧率 | 79–160 |
| 网易云各进程 CPU 合计 | 200–240%（单核 100%），其中页面进程 125–155% |
| 网易云 GPU 进程的 3D 引擎 | 12–38% |
| 网易云 GPU 进程专用显存 | 1.2–1.6 GB |

GPU 远没有跑满，帧率卡在页面主线程上。后来查明这是当时整机被别的会话的视频渲染和内存压力拖慢：机器空下来后（04:28 重测，优化后的版本），同一窗口不限帧率 190–290 帧，每帧 CPU 0.5–0.7 ms，GPU 中位 0.6–1.3 ms（见 [TESTING.md](TESTING.md)）。只记 CPU（`mode: 'cpu'`，不发 GPU 查询）和带 GPU 查询的帧率相差不大，测量本身不是瓶颈。这一轮之后的测量被打断（BetterNCM 在 `plugins_dev` 变化时会重载页面），其余场景改在无头 Edge 里测。

### 热点（无头 Edge，37 个场景，优化前 → 后）

每帧 GPU 中位，1813×1176：

| 场景 | 优化前 | 优化后 | 主要花在 |
|---|---|---|---|
| 夜城 | 4.8 | 3.7 | 场景本身 3.0（地面着色器），景深 0.9 → 0.5 |
| 光斑 | 4.0 | 3.1 | 场景本身 2.7 |
| 三角 / 悬城 / 门格回廊 | 3.1 / 2.7 / 2.5 | 2.3 / 1.9 / 1.8 | 分形光线步进 1.7–2.3 |
| 云海 | 3.3 | 2.3 | 光线步进 2.1 |
| 雨窗 | 3.3 | 2.1 | 场景本身 1.9 |
| 极光、光柱、浮雕、唱片、细分 | 2.0–2.6 | 1.3–2.0 | 景深 / 运动模糊 0.3–0.8 |
| 其余 26 个 | 1.1–2.0 | 0.6–1.3 | 后期占一半以上 |
| 37 个场景的中位 | 1.65 | 0.71 | |

改前每个场景都有约 1.1 ms 的固定后期开销（grade 0.45、泛光 0.25、光拖尾 0.23、文字层 0.14），比大多数场景本身还贵。按风格整段（自动编排、drop 段 4 秒 × 3，两轮平均）：律动 2.1 → 1.0，抒情 3.4 → 2.1，字 1.6 → 0.7，墨 1.7 → 0.8 ms；画风在主歌段另加 0.2–0.6 ms。p95 约是中位的 2–3 倍，主要是转场（两个场景同时画）。

分辨率：律动在这块卡上低于约 0.95 MP 后就不再变快（约 0.6 ms 是固定开销），抒情基本按像素数线性（1813×1176 1.67 ms → 846×548 0.43 ms）。弱显卡上更接近线性。关泛光省约 0.17 ms，关镜头和成片后期合计省约 0.17 ms。

### 已做的优化

1. **后期缓冲不再用 4× MSAA**（`engine.ts`、`shots.ts`）。composer 的两个缓冲原来是半精度 + 4× MSAA + 深度，之后每个全屏通道（泛光合成、grade、成片）都写进多重采样缓冲再解析一次颜色和深度，纯属浪费；两块缓冲在 1080p 下还占约 220 MB。改成单采样、无深度；场景本身仍画进 ShotPass 自己的 MSAA 缓冲，“无镜头、无转场”时先画进 rtB 再拷过去。每帧 GPU 中位 1.65 → 0.89 ms。渲染缓冲显存 1080p 约 680 → 490 MB，4K 约 2.7 → 2.0 GB。
2. **渲染目标的采样改用 `textureLod(…, 0.0)`**（grade、镜头、转场的 tA/tB、画风）。D3D 编译器（FXC）对分支和循环里带梯度的采样会把分支压平执行：grade 的缩放模糊（10 次）、拖影（12 次）循环每个像素都在跑，0.30 → 0.15 ms。渲染目标没有 mipmap，结果逐像素相同；封面和字形图集有 mipmap，不改。合计 0.89 → 0.71 ms。
3. **歌词碎成粉尘时不再读回 GPU 画布**（`text.ts` 的 `inkPoints`）。原来每个词第一次碎掉时对整张文字画布 `getImageData`，加速的 2D 画布要从 GPU 读回，一行字可达几十到上百毫秒（夜城段 60 帧里耗了 177 ms）。现在按同样的笔画在约 9000 像素的小画布上重画再取点，约 2 ms。取到的点与原来相距 1–2 个纹理像素，粒子数由词宽决定，看不出差别。
4. **预热补上播放中才编译的材质**（`textPrimer` / `primer`）。粉尘粒子、带贴图的文字、“写入”效果的文字、光斑里可虚焦的文字，原来都要等第一次出现才编译，卡 100–150 ms。现在叠加层和各歌词组里各放一个隐藏的样本：预热会编译隐藏物体，样本也一直持有程序。样本的包围盒设为空，否则会改变镜头对焦（对焦用歌词组的包围盒）。
5. **换歌时释放场景的私有资源**（`MvScene.dispose`）。歌词印层（翻牌、半调、水墨、雨窗、碎片）、画布的两张绘画缓冲和内部场景、云海和分形的光线步进缓冲、光柱的状态缓冲都不在场景树里，卸载时碰不到，每首歌都留下一份（反复重新编排 24 次，几何体 596 → 1076、纹理 330 → 486，渲染缓冲另算）。现在各场景实现 `dispose()`，`MvPlayer.unload` 调用；只释放几何体、材质和自己的缓冲，不释放纹理（云海的噪声体是按渲染器缓存、跨歌复用的）。

画面对比：每项改完都和 HEAD 的代码在同一首歌、同一 seed、同一时刻逐像素比对（4 种风格 × 42 个时刻，37 个场景 × 3 个时刻）。差异只在两处：叠加层线条端点上原来靠 MSAA 抹平的几个像素；正在碎成粉尘的词，粒子是从取样点里随机挑的，挑中的不同。两处肉眼都看不出来。

### 自动画质（2026-10-17，下一版）

画质的“自动”档，默认选它：按 MV 每帧在显卡上的实际耗时，在三档像素比之间切换。代码在 `src/app/governor.ts`，帧循环里的接入是 `src/plugin/main.ts` 的 `govern()`。

- **档位**：第一档就是“高”（屏幕原生，最高 2 倍），每降一档约少 30% 像素，最低是一半像素，景深和动态模糊一直保留。150% 缩放的屏幕上是 1.5 → 1.26 → 1.06 倍，100% 的屏幕上是 1 → 0.84 → 0.71 倍。最低档是用户看过对比图（`dev/bench/stills/quality/`，不入库）后定的：0.89 倍起文字和细线明显变软。更弱的显卡要手动选“中”或“低”。
- **量什么**：插件自己每帧的 GPU 时间（`EXT_disjoint_timer_query_webgl2`，一帧一个 TIME_ELAPSED 查询，结果晚几帧取回），转场帧（同时画两个场景）不计。没有这个扩展时改看帧间隔，只降不升。别的程序占用显卡不算在内：它们的绘制排在插件的两帧之间，插件这一帧的 GPU 时间不变。另开一个页面占去约七成 GPU 实测过，网易云的帧率掉了，测到的耗时没变。所以“自动”只在 MV 本身画不动时才降。
- **何时降**：只在切镜时换档，一组连续运镜的镜头中间不换。最近约 2 秒里较慢的四分之一帧超过 60 帧预算（16.7 ms；帧率上限 30 时 33.3 ms）的 85% 就降一档，换档后 3 秒内不再动。
- **何时升**：在当前档停满 15 秒，并且换档以来每个镜头较慢的帧（p90）按像素换算到上一档后，仍留出三分之一预算。升上去不到一分钟又降回来，下次升档的等待加倍，最长 4 分钟。场景之间的耗时能差好几倍，只看最后一个镜头时，在模拟的 GTX 1650 一级显卡上，抒情和字会在轻场景升档、到下一个重场景又降回，40 秒里来回 4 次；改成看换档以来的所有镜头后，同样的负载下 12 段各 3 分钟没有一次降了又升。
- **测量时关掉**：TIME_ELAPSED 查询不能嵌套。`tools/bench/inpage.ts` 注入时把 `window.__betterMv.governed` 设为 false，测量自己定分辨率；看插件自己播放的几组（long、switch 等）因此按“高”测。
- **不降档时画面不变**：第一档就是“高”的像素比，计时查询不影响绘制。无头 Edge 里 4 种风格 × 8 个时刻与 HEAD 逐像素对比，个别像素差 1 级，HEAD 自己重跑一遍也是这样。

实测记录在 [TESTING.md](TESTING.md)“自动画质”。

### 还没做 / 没弄清的

- **换歌时主线程卡 0.5–1.3 s**：已改（建场景和预热分片、准备中的歌不画，见“准备时间”一节的“换歌时的长任务”），网易云里准备期间最长不出帧 0.54–1.11 s → 63–143 ms。弱 CPU 上能不能 60 帧也还没实测。
- **集显实测**：要在混合模式（MUX 切回）或别的机器上用 `tools/bench/run.ts` 跑一遍。
- **自动画质的真机实测**：只在本机上用放大像素比和缩小预算模拟过慢显卡（见下一节），集显和 GTX 1650 一级的真机上，档位够不够、换档频率是否合适还要复测。
- **剩下的单帧尖峰**：一个“带贴图、无法线”的网格在律动某处第一次出现时才编译，播放结束前已释放，没追到是谁；墨风格竖排新句子出现时 CPU 约 70 ms（字形绘制）；另有 15–40 ms 的纯 GPU 尖峰，可能是新文字纹理上传，也可能是别的进程在抢 GPU。
- **没有软件渲染提示**：网易云关了 GPU 加速时 WebGL 跑在 SwiftShader 上，插件可以按渲染器名称提示用户打开。

## 准备时间与着色器（2026-10-13）

从拿到音频到 MV 能播，依次是：解码 → 分析 → 建场景（`player.load`）→ 预热（`player.warm`）。

### 实测（2026-10-13）

《Falling Again》（33 MB FLAC，4 分 29 秒），dev 未打包，无头 Edge（ANGLE D3D11，RTX 5070 Ti 笔记本）：

| 阶段 | 改前 | 改后 |
|---|---|---|
| 解码 | 两次（22.05 kHz 单声道 + 44.1 kHz 立体声）约 0.8 s | 一次，约 0.4 s |
| 分析（V8） | 约 0.6 s CPU，分片之间等帧 | 约 0.45 s，分片之间不等帧 |
| 建场景 | 约 0.5 s | 第一首约 0.5 s，之后约 0.05 s（夜城楼群只生成一次） |
| 预热 | 4.9–5.4 s | 第一首 1.1–1.6 s，之后同场景几乎为 0 |
| 第一帧 | 卡片 107 ms、极光首次出现 147 ms | 约 20 ms，无尖峰 |

合计（音频到手后）约 7 s → 约 3 s。机器上有别的渲染任务时数字会翻 2–3 倍，比较只看同一时段的 A/B。测量脚本在会话的 scratchpad 里（`flow.ts` 全流程、`probe.ts` 单场景编译、`frames.ts` + `cmp.ts` 逐像素对比、`gpu.ts` 帧耗时），没有入库。

### 换歌时的长任务（2026-10-17）

网易云里连切 6 首（`run.ts switch`）时，每次换歌页面有一段 0.5–1.1 s 不出帧（等待页的动画停一下），总在 MV 第一帧前约 0.6 s 结束。无头 Edge 里用 `headless.ts switch` 复现：开发页按插件的路径换到网易云缓存里的另一首（`prepareSong` 全速、建场景、预热，新歌的帧按插件帧循环的规则才画），记长任务（PerformanceObserver）和动画帧间隔，`--cpu` 再把 CPU 剖析切到最长的几个任务上。3 首歌（各 20–24 个场景）每次 0.42–0.53 s 不出帧（机器忙时 0.5–0.7 s），由三段组成（《Cytus II Opening》，24 个场景，CPU 剖析和 Chrome 跟踪）：

1. **一个 0.25–0.36 s 的 JS 任务**（机器忙时 0.4–0.6 s）：`prepareSong` 收尾（`toStereo`、`xyMusic` 约 20 ms），`player.load`（场景构造：细分 41–52 ms、画布 34–52 ms、调试视图 28–37 ms、浮雕 17 ms，`setLooks` 的字形图集 23–33 ms），`warm` 的同步部分（24 个场景逐个摆到第一个镜头：画歌词文字、粉尘取点、频谱，光柱一个就 33–51 ms）。
2. **紧接着 0.15–0.29 s**：上一段画的 2D 画布在任务结束时一起提交（`CanvasRenderingContext2D::FinalizeFrame` → `RasterCHROMIUM` 183 ms，CPU 剖析里显示为 idle）；插件的帧循环在 load 之后就开始画新歌（等待页不透明，看不见），第一帧碰到还在并行编译的程序，`onFirstUse` 里的 `getProgramInfoLog` 同步等它编完。
3. **预热逐场景绘制，每个 50–180 ms**：`getProgramInfoLog` / `getProgramParameter` 同步等 GPU 进程做完上一个场景的活（上传纹理、绘制时才编的着色器变体）。

改法：

- **建场景分片**（`MvPlayer.loadInSlices`）：load 的内容改成生成器，同步的 `load()` 一次走完（开发页、OBS 页、片子、bench 照旧）；插件准备新歌时在规划镜头后、每个场景构造后、字形图集后各让出一次（`yieldToPage`）。准备被取消时卸掉建了一半的，另一次 load 开始时停下。
- **预热分片**：每个场景摆好后马上开始编译它的程序，场景之间让出；全部编完后逐个绘制，下一个等 GPU 做完上一个（`Engine.idle`：WebGL2 fence，在让出之间查看，最多等 1 s，连续超时 3 次后不再用）。绘制前先对已编好的程序读一次信息（`getUniforms`，此时 GPU 空闲），绘制本身就不再同步等待。
- **准备中的歌不画**：插件帧循环在这首歌预热完之前不画它（等待页盖着，原来画了也看不见），预热完再出第一帧。

网易云的 Chromium 91 跑这些 JS 比无头 Edge 慢 3–4 倍，上面分片之后在网易云里剖析，还剩几段单独就超过 0.1 s，也一并拆开：

- **单个场景内部分步**：画布的整首笔画规划（170–250 ms）每 1024 步让出一次，细分球的逐级细分（100–125 ms）每级让出两次，画风的字形图集（逐字绘制、读回量墨量，63–71 ms）每 64 个字让出一次。各自写成生成器（`CanvasScene.building`、`SubdivideScene.building`、`GlyphAtlas.building`），一次建完时用 `finish` 走完，结果逐位相同。
- **`prepareSong` 收尾**：封面取色、立体声的峰值、转换之间各让出一次（合起来 85–90 ms）。
- **OBS 输出的歌曲文件**（设置里打开了 OBS 输出时才有）：`JSON.stringify` 会先调用封面纹理的 `toJSON`，把整张图编码成 PNG data URL，再交给 replacer 丢掉，白耗 50–75 ms。现在不带纹理去序列化，封面的 JPEG 每首只编一次（找到逐字时间后还要再发一次），并且放在单独的任务里。生成的文件逐字节相同，200 ms → 24–29 ms。
- **等待页提前撤掉**：建场景期间如果又触发一次准备（例如打开 MV 页），会被当成“这首已经在显示”而撤掉等待页。现在这首还在建或在预热时不算。

结果，无头 Edge（`headless.ts switch`，1209×784@1.5，同样 3 首，改前改后交替各跑 2 轮）：

| | 改前 | 改后 |
|---|---|---|
| 最长不出帧（动画帧间隔） | 0.42–0.53 s | 没有超过 50 ms 的 |
| 超过 50 ms 的任务 | 每次 2–5 个，最长 0.25–0.36 s | 没有 |
| 读完音频到预热完 | 1.41–1.73 s | 1.34–1.64 s |

网易云（`run.ts switch` 连切 6 首，1813×1176，画质“高”，改前是 04:40 的同一测试）：

| | 改前 | 改后 |
|---|---|---|
| 准备期间最长不出帧 | 0.54–1.11 s | 63–143 ms，多数 50–100 ms |
| 准备期间超过 50 ms 的帧间隔 | 每次 8–40 个 | 每次 0–7 个 |
| 等待页（切歌到 MV 第一帧） | 2.5–8.8 s | 3.4–7.7 s |

切歌那一下还有一段 83–133 ms，是网易云自己处理切歌（redux 的分发与订阅），改前同样有（100–170 ms），插件在其中约 10–20 ms。

画面：`headless.ts stills`（37 个场景 × 3 个时刻、4 种风格整段 × 6 个时刻）和改前逐像素对比，每张平均差几十个像素、最多 2 级；改前的代码自己跑两遍也差这么多（每张 29 个像素、最多 3 级，墨的个别时刻在两种结果之间随机出现，重跑即与改前相同）。分步建的和一次建的同一首歌、同一 seed、同一起始状态，7 个时刻对比，同样只在噪声范围内；字形图集（3 段文字）逐像素相同。分析结果：`bun run eval` 改前改后逐项相同（分析代码没改）。

“卡在正在准备画面 90%”：自动画质会话在网易云里遇到过一次，停了 5 分钟以上。之后在网易云里换歌约 38 次（手动切 25 次，打开“提前分析下一首”后让歌放完自动切 13 次）没有再出现。查代码只找到上面那处提前撤掉等待页，并补了两处防护：建场景被别的加载打断时改为一次建完；关掉再打开 MV 时，被取消的准备不再挡住新的准备。

剩下的：

- 网易云里单独超过 50 ms 的几段：调试视图的地形网格构造 57–85 ms（含垃圾回收），封面取色约 53 ms，准备末尾偶尔 100–143 ms（没剖析到是哪一段）。弱 CPU 上按比例变长，再拆要改这几个场景本身。
- 光柱、声道的摆位里，粉尘取点的 `getImageData` 在 GPU 忙于编译时要等 35–45 ms（平时约 2 ms）。换成 CPU 画布（`willReadFrequently`）可以不等 GPU，但 124 个词里有 43 个取到的点差一两个，粉尘的样子会变，没改。
- 设置改动后的重新编排、“换一种”仍是同步建场景、边画边预热（MV 正在显示，不能停画），会顿一下，没改。

### 着色器编译（最大头）

网易云的 Chromium 在 Windows 上把 WebGL 翻成 HLSL，由 D3D 编译器（FXC）编译，很慢，而且**每个函数调用都内联、常数次数的循环都展开**。夜城地面的着色器里 `lightRow` 写了三十多处调用，一个程序编译 2.2–2.4 s。

- **并行编译**：`Engine.compile` 用 three 的 `compileAsync`（`KHR_parallel_shader_compile`），所有场景的程序在 GPU 进程里一起编、页面不卡；`warm()` 之后只剩上传缓冲和纹理。没有这个扩展时退回同步编译，不会更差。
- **场景自己的离屏通道**（`onBeforeRender` 里另画的场景或全屏四边形）不在场景树里，`compileAsync` 找不到：在 `MvScene.offscreen` 里列出来（全屏四边形用 `passMesh(material)`）。云海、画布、光柱、分形图版都这样做。
- **后期链**（泛光、调色、转场、画风）用 `Engine.compilePost`，屏幕和离屏两种目标都编（程序随目标不同）。
- **颜色用 uniform，不写进源码**：源码随封面变，每首歌都得重编；源码不变，同一次使用里第二首起直接复用程序。夜城、极光已改（数值按原来写进源码时的位数取整，画面逐像素不变）。跨重启的磁盘缓存在当前 Edge 上没测到命中，不指望它。
- **提前编译**：源码与歌无关之后，夜城、极光和后期链在 `MvPlayer` 构造时就开始编（插件里播放器在读歌、分析之前创建），和准备阶段重叠。
- 试过把夜城的重复调用收进循环、参数查表：编译 2.2 → 0.7 s，但运行时每帧多 0.3–0.4 ms（+11%，展开的 16 次大街循环反而快），撤回了。新写的着色器仍应避免同一个重函数写几十处调用：能写成一个循环里调一次的，就别展开写。

### 解码与准备

- 只按 22.05 kHz 解码一次，分析的单声道、示波器的立体声都从这里来；左右声道差异大到可能是示波器音乐时（`xyMusic` 的第一关 > 0.3，很少见）才按 44.1 kHz 再解一次做完整判断。
- V8 里的坑：循环里读 `AudioBuffer.numberOfChannels`（每次都是一次 DOM 调用）让下混慢了十倍；`Math.round` 一千多万次约 0.1 s，`toStereo` 换成截断写法。
- 试过按 44.1 kHz 解码再用 JS 半带滤波降到 22.05 kHz（浏览器解码时顺带重采样约多 0.1–0.2 s）：分析结果几乎一样，但 JS 降采样本身 80–275 ms，抵掉了收益，没用。

### 分析

- FFT（`fft.ts`）：前两级（旋转因子 1、−i）并进位反转，其余每两级一趟、分级连续存放的旋转因子表；V8 里 1024 点 9.1 → 4.9 µs。`quantile` 用快速选择代替整段排序。改前改后 5 首本地歌的评测输出逐项相同。
- 分片之间用 `yieldToPage`（MessageChannel）让出，不等 requestAnimationFrame：原来每 8 ms 工作后等一帧，一半时间空等；网易云最小化时 rAF 停掉，分析也跟着停。
- 剩下的热点：STFT 本身（约一半）、tempogram 的自相关、onset。

### 提前分析下一首（设置 `prefetch`，默认关）

- `main.ts` 的 `prefetchNext`：当前歌准备完、开关打开、播放列表或位置变化时，用 `client.ts` 的 `nextSong` 找下一首（顺序播放、列表循环；单曲循环、随机、FM、AI 模式无法预知，不做），在后台 `gather`（读音频、歌词、百科、封面 → `prepareSong`），完成后放进 `ready`。
- 节奏：`whenIdle`（requestIdleCallback，最迟 0.5 s）+ 3 ms 分片，只用帧与帧之间剩下的时间。无头 Edge 实测：边播 MV 边预读，帧间隔没有变差（最长 23 ms，单独播放时 37 ms），约 0.9 s 准备完。还剩几段同步计算（单声道下混、`toStereo` 各约 20 ms），预读时可能丢一两帧。
- 预读没完成就切到这首：`prepareCurrent` 接手同一个任务，改成全速（`yieldToPage`）并显示进度；切到别的歌、关掉 MV 或关掉开关就取消。
- 首次歌词对齐改在歌真正显示时（`alignIfNeeded`）：预读的歌把音频留到那时（`toAlign`），看过一次就释放。
