# 右键菜单与下载 MV

## 右键菜单

代码在 `src/plugin/menu.ts`（`Menu`、`Notice`、`ask`），样式在 `uiStyle.ts` 的 `bmv-menu` / `bmv-notice` / `bmv-alert`，菜单内容由 `main.ts` 的 `menu()` 在每次打开时生成。

| 分组 | 项 | 说明 |
|---|---|---|
| 播放 | 播放 / 暂停、喜欢 / 取消喜欢 | 未登录或私人 FM 等拿不到喜欢状态时不显示“喜欢” |
| 编排 | 换一种编排、风格 › | 风格子菜单与设置里的“风格”同一项配置；下载进行中两项都禁用 |
| 输出 | 保存当前画面、下载 MV… | “下载 MV…”打开导出面板；下载进行中换成“取消下载” |
| 界面 | 显示控制栏 ✓、设置…、退出 MV | 下载进行中退出 MV 不取消下载，进度改在进度条上显示 |

- 在画面或控制栏上右键弹出；设置面板和更新窗口里不弹。
- 菜单左上角在光标处，靠右边缘时改到光标左侧，靠下边缘时整体上移；子菜单放不下时开到左侧。
- 悬停即打开子菜单；子菜单开着时移到父菜单的另一项要停 160 ms 才切换，斜着移向子菜单时不会被经过的项关掉。
- 键盘：↑ ↓（Tab）移动，→ 进入子菜单，← 返回，回车或空格选中，Esc 先关子菜单再关菜单（不退出 MV）。
- 选中后该项闪一下（熄 70 ms），菜单淡出，140 ms 后执行。点菜单外只关闭菜单，这次点击不传给下面的元素：覆盖层保留到松开鼠标之后 250 ms，期间的右键会在新位置重新打开菜单。
- 菜单或确认框开着时控制栏和光标不自动隐藏。
- 动效只用 opacity / transform（打开 90 ms 淡入，关闭 160 ms 淡出），关闭后用定时器移除节点，不依赖动画结束事件（后台页面不跑动画）。
- 子菜单和主菜单一起建好、一次读完尺寸并定位，先隐藏；悬停只把它显示出来，不建节点、不读布局。MV 页打开后约 1.8 s，在看不见的地方把菜单画一遍（`Menu.warm`），让子菜单里的字提前完成排版和绘制。原先悬停时才建子菜单，要同步布局并第一次排版“抒情、字、墨”等字，网易云里整个菜单会卡一下。模拟网易云负载（CPU 降速 4 倍、每帧另占 8 ms）实测：首次悬停“风格”时最长的帧间隔从约 75 ms 降到 11 ms，右键打开菜单从约 55 ms 降到 23 ms。
- 隐藏的子菜单用 `visibility: hidden`，里面的元素不能写 `visibility: visible`（会透出来），勾选标记因此用 opacity 显隐。

## 下载 MV

把当前歌曲的 MV 逐帧渲染成 MP4：画得多快就导多快，不跟播放走，不用等整首歌。网易云内核是 Chrome 91，页面里只有 MediaRecorder 能编码视频，且它在网易云里拿到的是 Windows 自带的软件编码器，按“30 帧、Baseline、无 CABAC”配置，抬高码率画面仍有色块。所以编码交给插件自带的本机程序 `bettermv-encode.exe`，由它调用 Windows 的 Media Foundation（有显卡编码器时用显卡，否则用 Windows 自带的软件编码器，High 档、带 B 帧）；程序起不来时退回 MediaRecorder（[兼容模式](#兼容模式mediarecorder)）。

| 文件 | 内容 |
|---|---|
| `src/plugin/exportOptions.ts` | 选项、画面尺寸、码率、范围、预计大小和耗时、设置里的保存 |
| `src/plugin/exportSheet.ts` | 导出面板（`overlay.dialog`） |
| `src/plugin/export.ts` | 逐帧渲染、送帧 |
| `src/render/nv12.ts` | 在显卡里把画面打包成 NV12，批量读回 |
| `src/plugin/encoder.ts` | 启动编码程序、和它通信 |
| `src/export/helper/BetterMVEncode.cs` | 编码程序 |
| `src/plugin/pill.ts` | MV 页关闭时的进度条 |
| `src/plugin/video.ts`、`mux.ts` | 兼容模式：MediaRecorder + 自写 MP4 封装 |
| `tools/export-test.ts` | 无头 Edge 里跑一遍导出并和原帧比对 |

### 选项

保存在插件设置的 `export`（JSON）里，下次打开面板沿用；上次每帧的耗时存在 `exportSpeed`，用来估计“预计”。

| 选项 | 取值 | 说明 |
|---|---|---|
| 画幅 | 横屏 16:9、竖屏 9:16、方形 1:1 | 引擎按这个尺寸画，各场景会按画幅重新构图 |
| 清晰度 | 720p、1080p、4K | 短边的像素数；横屏 1280×720 / 1920×1080 / 3840×2160，竖屏相反 |
| 帧率 | 30、60 | 30 帧时每个输出帧前仍按 60 Hz 多画一帧：场景里的拖尾和缓动是按 60 Hz 做的，只画 30 步它们会变样 |
| 画质 | 标准、高、极高 | 每像素每帧 0.10 / 0.16 / 0.26 比特，1080p 60 帧约 12 / 20 / 32 Mbps；30 帧乘 1.25，限制在 2–60 Mbps |
| 范围 | 整首、副歌、自定义 | 副歌取歌曲第一个“副歌”段（没有则第一个“高潮”，再没有则前 30 秒），最长 90 s；自定义填起止时间，至少 1 s |
| 编码 | 自动、显卡、处理器 | 自动与显卡都先试显卡编码器，试不通再用 Windows 自带的；处理器直接用后者 |

面板还显示按这些选项得到的尺寸、码率、文件大小和预计时间。

选“副歌”时多出一行起止时间，选“自定义”时多出两个时间框：这些行用高度和透明度过渡（`setOpen`，进 320 ms、出 260 ms），面板居中，随之伸缩，不再一下子跳大。曲线用 `cubic-bezier(.4,0,.2,1)`（起步和收尾都是静止的）：页面其余动效用的 `--ease` 起步就是全速，适合“到来”，不适合一个框被拉长。收起时的行先淡出再 `display: none`（里面的输入框不再能被 Tab 到）；动画中途反向会从当前高度接着走；系统要求减弱动效时直接切换。动画在主线程上改高度（面板只有一二十个节点，改动 20–30 px），在无头 Edge 里按网易云的负载模拟（CPU 降速 4 倍、每帧另占 8 ms）测过：最长的帧约 17 ms，对照不动时 9.5 ms。无效的时间框边框变红也有 150 ms 过渡。
输出保存到网易云下载目录（`Storage.downloadDir`）下的 `BetterMV\歌名 - 歌手[ 起-止][ 竖屏|方形].mp4`，拿不到下载目录时用 BetterNCM 数据目录下的 `BetterMV\MV`，重名加 ` (2)`。

### 流程

1. `openExport` 打开面板，选定后 `startDownload`：`getAudio` 读整首歌，`exportNative` 里用 `OfflineAudioContext(2, 1, 44100).decodeAudioData` 解码。
2. 引擎改为所选尺寸、像素比 1（`Engine.fixedSize`）。
3. 启动编码程序，`begin` → `audio`（范围内的 16 位 PCM）→ 一批一批送帧 → `finish`。
4. 每帧：`player.frame(t, 1/60)` → HUD（HTML，要另画一份）画到一张透明 2D 画布 → 显卡里把画布内容和 HUD 打包成 NV12，放在批的第 k 块。一批 6 帧（尺寸太大时更少：批高不能超过 `MAX_TEXTURE_SIZE`）。从歌曲中间开始的片段，先画并丢弃前 1 秒，让拖尾和缓动就位。
5. 一批画完，`start` 让显卡把它拷进像素缓冲，再取走上一批（`finish`），作为一个请求发给编码程序。
6. 整首送完调 `finish`，编码程序写完文件才回答；提示条（MV 页关着时是进度条）给出“在文件夹中显示”：`app.exec('explorer /select,' + execArg(路径), false, true)`（转义引号和 `showWindow` 的原因见 [CLIENT.md](CLIENT.md) 的 `app.exec`）。

渲染不跟页面绘制走：同一个任务里画完就读，每秒能画多少帧只看显卡和送帧速度，不再被屏幕刷新率限制。

### 编码程序

`BetterMVEncode.cs`，用 .NET Framework 4.x 自带的 csc 编译（`scripts/build-encode.ps1`，26 KB，不依赖 ffmpeg 或编解码包），随插件放在 `export\`，运行时复制到 `<数据目录>\BetterMV\export\` 再启动（插件文件夹每次启动都重新解压，运行中的程序文件被占用），做法同 OBS 程序。一次下载起一个，结束时 `quit`；网易云退出时自己结束（先给写入线程 1.5 s 删掉没写完的文件）。直接 P/Invoke `mfplat.dll`、`mfreadwrite.dll`，用 `IMFSinkWriter`；接口手写声明，派生自 `IMFAttributes` 的接口要把它的 30 个槽重写一遍（托管侧按接口自己声明的方法排虚表，不含继承来的），`IMFSinkWriter` 的 IID 末位是 `d`。

只在本机 HTTP，参数 `--port`、`--key`、`--version`；除 `GET /api/status` 外都要 `x-bmv-key`，网页（http / https 来源）一律拒绝，只有网易云自己的页面（`orpheus://`）能用；`--dev-origin` 让开发服务器的页面也能用（`tools/export-test.ts`）。

| 请求 | 内容 |
|---|---|
| `POST /api/begin` | JSON：路径、宽高、帧率、码率、音频采样率 / 声道 / AAC 码率、是否试显卡编码。先用临时文件探测（显卡编码器能否用，AAC 编码器在不在，不行退到软件，再不行报错），再开真正的文件；MP4 的 moov 放在前面。回 `{encoder}` |
| `POST /api/audio` | 整首 PCM（16 位小端、交错），空内容表示无声；必须在第一帧前 |
| `POST /api/frame` | 头 `x-bmv-i` 是第一帧的序号，内容是连续的若干帧 NV12（每帧宽×高×3/2 字节）；请求可乱序、同时在途几个，写入线程按序号写，落后太多时挂住请求，发送方因此被限速 |
| `POST /api/finish` | 头 `x-bmv-frames`；等文件写完，回字节数、帧数、用时、编码器 |
| `POST /api/cancel`、`/api/quit` | 停下并删掉没写完的文件；退出 |

启动：`app.exec` 的调用最多等 2 秒（Windows 因为程序被安全软件占用、文件缺失而弹对话框时，这个调用会一直开着，下载会跟着等下去），之后 6 秒内没有应答就放弃、不再换端口试，改用兼容模式（约 8 秒后开始）。

音频每写完一个视频帧，就把对应时间之前的 PCM（至少 4096 个样本一块）交给 AAC 编码器，音视频按时间交错。输出：H.264 High，BT.709 受限范围（矩阵、原色、传输特性都标上），每 2 秒一个关键帧；AAC-LC 256 kbps、44.1 kHz。用 1.000 s 处的一声脆响和第 60 帧的一个白帧测过：两种编码器下音视频都落在 1.0000 s。出错写到临时目录的 `bettermv-encode.log`。

### 在显卡里打包 NV12

`Nv12Packer`：引擎画完的画布用 `renderer.copyFramebufferToTexture` 拷成纹理，一个全屏着色器按 BT.709 受限范围算 Y，色度取 2×2 平均，写进宽 w/4 的 RGBA8 目标：每个纹素是 NV12 缓冲里连续的 4 个字节（先是 Y 平面，再是 U、V 交错的行），所以读回的像素就是 NV12，行距等于宽。HUD 纹理（预乘 alpha）在着色器里叠在画面上。1080p 一帧 3.1 MB，RGBA 要 8.3 MB。

不在页面 JS 里转换：网易云里 JS 慢 3–4 倍，200 万像素一帧转不过来。

### 读回与送帧：实测出的几个限制

- **读回是同步的，而且排在后面。** `getBufferSubData` 在显卡空闲时拷 3.1 MB 只要 1.1 ms，但它排在已提交的命令后面，管线里每帧都要等后面的帧画完，实测 6–8 ms。所以一批 6 帧一起打包、一次读回、一个请求：单帧版 38 帧/秒，批量后 117–125 帧/秒。取走“上一批”而不是刚画完的这一批，等待最短。
- **请求体必须是 Blob。** `fetch` 的 body 传 `ArrayBuffer`，无论哪个服务器都只有约 33 MB/s；传 `new Blob([bytes])`，一批 18 MB 能到约 390 MB/s（`XMLHttpRequest` 同 `ArrayBuffer`，WebSocket 约 110 MB/s）。送帧速度的上限就是它。
- **Blob 的内存要自己管。** Blob 的数据留在浏览器里，直到页面的垃圾回收发现这个 Blob 对象没人用了；这个页面几乎不分配，回收很久不来，导出 600 多帧（约 2 GB）后 `fetch` 报 `net::ERR_BLOB_OUT_OF_MEMORY`（无头 Edge 里；带磁盘的配置会把 Blob 写盘，同样要避免堆积）。两件事都要做，缺一不行：每个请求的响应读到底（`Encoder.call`，未读完的响应一直拿着请求体）；每发 160 MB 就分配并丢弃一个 96 MB 的 `ArrayBuffer`，V8 把它算作堆外内存而回收（`collectBlobs`）。
- 不用 `setTimeout` 轮询：后台页面里它被限到 1 秒一次。让出线程用 `MessageChannel`（`tick`）。
- 同时在途的请求最多 3 批，每个请求固定耗时约 10 ms，所以不能一帧一个请求。
- 显卡编码器在这台电脑上会和渲染抢显卡：单帧版里显卡编码比软件编码慢一倍（38 对 79 帧/秒），批量后两者接近（117 对 100）。

### 测试

`bun tools/export-test.ts [--id 歌曲ID] [--from 40] [--to 50] [--size 1920x1080] [--fps 60] [--mbps 24] [--ref 120,400] [--hw 0]`：在无头 Edge 里用开发页（自己起一个 5197 端口的服务器）跑 `exportNative`，音频取自网易云缓存，输出到 `dev/export/`，再取几帧和引擎当时画的原帧比 PSNR / SSIM。原帧不含 HUD，所以 HUD 的角落会有差。需要先 `scripts/build-encode.ps1`。颗粒和碎片多的画面 PSNR 只有 22–31 dB，是颗粒编不进去，用 100% 放大看：边缘、文字干净，没有色块。`settings.html?mv` 里的“下载 MV…”打开真实的导出面板（进度是模拟的），`?mv&pill` 显示进度条。

### 限制

- 最小化时页面是 `document.hidden`：下载照常进行（用的是 `MessageChannel` 和 `fetch`，不靠定时器和页面绘制），但画帧变慢，实测 49 帧/秒，前台是 172。
- 下载期间播放器在画下载的帧，MV 页不显示画面（关着 MV 页时没有影响）；网易云照常播放，切到下一首时等下载结束再准备新歌。
- 退出 MV 页不取消下载：MV 页关着时，进度显示在播放栏上方的进度条上，点进度条回到 MV 页，“取消”取消下载；关闭网易云会取消，没写完的文件删掉。取消后文件在编码程序里被收尾、释放再删除；`quit` 要等这一步做完（最多 20 s）才退出：进程先退出时没写完的文件会留在下载目录里（实测过）。
- 4K 竖屏一帧 5760 行，一批只能装 2 帧；4K 对显存要求高（引擎的后期缓冲在 1080p 就占 200 MB）。
- 系统没有 H.264 / AAC 编码器（N 版 Windows 没装媒体功能包）或程序被安全软件拦住时，退回兼容模式：整首、1080p、60 帧，较慢，画质较低。

## 兼容模式（MediaRecorder）

代码在 `src/plugin/video.ts`（逐帧渲染、编码）和 `src/plugin/mux.ts`（读 WebM、写 MP4）。输出 1920×1080、60 帧的 MP4：H.264（Constrained Baseline）不低于 12 Mbps，MP3 320 kbps / 44.1 kHz。

网易云内核没有 WebCodecs，MediaRecorder 按帧到达的时间打时间戳，按真实时间录就要等整首歌。所以渲染不跟播放走，第 i 帧固定画歌曲的 i/60 秒，能多快就多快；MediaRecorder 只当压缩器用，它的时间戳全部丢掉，封装时按帧序重写。

1. `getAudio` 读整首歌，解码；引擎固定 1920×1080、像素比 1；等待页盖住画面，进度线按歌曲段落显示进度、剩余时间和“取消”。
2. 每帧在 requestAnimationFrame 回调里：`player.frame(i / 60, 1 / 60)` → `drawImage` 到 2D 画布 → `Hud.draw` → `requestFrame()`。画布捕获发生在这次页面绘制，所以一次页面绘制只能画一帧：在普通任务里画会被下一个 rAF 里画的帧覆盖，丢一帧。这是兼容模式比 Media Foundation 路径慢的原因之一。
3. 每帧之后编码这一帧对应的音频（lamejs，主线程，约 1.5 ms/帧）。lamejs 是经典脚本，用 `new Function` 执行（页面 CSP 允许 eval，不允许 blob Worker）。
4. MediaRecorder 每 25 ms 交出一段数据，`WebmReader` 边收边记下每帧在流中的位置（不保留帧数据，帧数据留在录制器的 Blob 里）。
5. 结束后写 MP4：`ftyp`、`moov`（放在前面）、`mdat`，音视频每秒交错一块。Chromium 写的 H.264 是 Annex B 且没有 CodecPrivate：按 16 MB 一段读出，转成 4 字节长度前缀，SPS / PPS 取出做 `avcC`，转好的段立即包成 Blob（不占页面内存）。MP3 加 edit list 跳过编码延迟 1105 个样本（LAME 的 576 加解码器的 529）。
6. `betterncm.fs.writeFile` 写入。

### 码率

MediaRecorder 的 `videoBitsPerSecond` 怎么花，取决于 Chromium 选了哪个编码器，两种都遇到过：

| 编码器 | 在哪 | 分配方式 | 传的码率 | 送帧速度上限 |
|---|---|---|---|---|
| Windows 自带的 “Microsoft H.264 Encoder”（Media Foundation 软件编码） | 网易云（Chromium 91） | 按帧到达的时间：每帧 ≈ 码率 × 与上一帧的间隔 | `BITS × 2` | 2 倍速（120 帧/秒） |
| 硬件编码器 | 新版 Edge | 每帧 ≈ 码率 / 30，与到达快慢无关 | `BITS × 30 / fps` | 4 倍速 |

- Windows 编码器在关键帧的 SEI 里写着自己的名字和配置（`fps:30.000 pf:66 gop:30 rc:1 rate:… cabac:0 lat:1`）：按 30 帧/秒配置、每 30 帧一个关键帧、Baseline、不开 CABAC。实测 30 帧/秒送帧时每帧正好是码率 / 30；按“码率 / 30”给 6 Mbps，导出时送帧约 130 帧/秒，每帧只分到约 6 KB，视频只有 4 Mbps，P 帧 QP 41–48（画面糊、有色块）。
- 选哪个编码器会变：低于 640×480 时 Chromium 改用 OpenH264（不写名字）；同一页面里，导出前的 3 帧试录拿到的编码器也和随后的导出不同。所以从导出自己的录制里认：第二帧到来前在数据里找 `Microsoft H.264 Encoder`，和假设不符就按另一种码率从第 0 帧重录（只浪费几帧），结果记到会话结束。
- 按时间分配时，送帧达不到 2 倍速（画面重、机器慢）每帧只会分到更多：整首实测 82 帧/秒，视频 17.4 Mbps，P 帧 QP 35–39。
- 用噪声测码率规律不可行：Windows 编码器对噪声在任何码率下都停在最粗的量化，每帧大小几乎不变。
- 画质看 QP，不看平均码率：`ffmpeg -debug qp` 打出每个宏块的 QP。
- VP9 / VP8 只在没有 H.264 时使用，也按时间分配。

### 背压与丢帧

- 已给出、还没从录制器读回的帧（在途帧）一开始最多 10 个：Chromium 编码队列超过约 10 帧开始丢帧，不限制时 VP9 会丢一半。
- 有的编码器要压着十几帧才开始往外吐（Edge 的硬件编码器有时如此）：10 帧时两边互相等，录制停在原地，直到停止时一次吐出。所以 0.4 s 没有输出就把窗口加宽 8 帧；窗口满而等待超过 15 ms 时加宽 2 帧（这时窗口决定速度）；最多 120。
- Chromium 偶尔丢一帧，读回的帧数会永远少于给出的帧数：按“给出数 − 读回数”判断会在累计约 10 次丢帧后永远等下去。所以按读回帧的时间戳找它对应的已给出帧。
- 发现丢帧时，送帧间隔拉长 30%、窗口收回 4 帧；连续 30 帧没丢再缩短 10%，不快于送帧速度上限。显卡同时在编码别的东西（远程桌面推流等）时，编码能力会随时变。
- 封装时帧数对得上就按顺序放；对不上时按时间对应，丢帧处前一帧延长。
- 录制器出错，或窗口已到最宽仍 15 s 没有输出，下载失败并在控制台记下状态。每次下载结束在控制台记一行：帧数、用时、丢帧、编码器、码率、在途帧上限。
